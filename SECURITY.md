# SelamPath Security Guide

This document describes the security model for SelamPath and its AccessPath career module,
the controls implemented in this repository, and the checks required before a production
deployment.

## Threat Model

SelamPath handles learner identity references, contact details, accessibility preferences, and
job applications. The primary risks are:

1. **Account takeover** through public registration or credential stuffing.
2. **Cross-site scripting (XSS)** through names, document numbers, job posts, or error text.
3. **Verification bypass** so an unverified contact can register.
4. **Session theft or replay** from long-lived tokens and missing logout.
5. **Abuse of paid or sensitive endpoints** (SMS, TTS, STT, AI, login, OTP).
6. **Data exposure** from committed databases, verbose errors, or permissive CORS.

## Implemented Controls

### Authentication and accounts

- Onboarding uses `INSERT` only. A duplicate `full_name` returns `409` and can never
  overwrite an existing password hash.
- Passwords are hashed with scrypt and a per-user random salt; comparison is constant-time.
- Login performs a hash derivation even when the account does not exist to reduce timing leaks.
- Sessions are random 256-bit bearer tokens, expire after `SESSION_TTL_DAYS`, are capped at
  10 per account, and can be revoked with `POST /api/v1/auth/logout`.
- Passcodes are never written to `localStorage`; legacy stored values are deleted on load.

### Contact verification

- `POST /onboarding/submit` requires a contact that was verified within
  `VERIFICATION_TTL_MINUTES` and is then consumed exactly once.
- The legacy client-supplied `otp_verified` field is accepted for compatibility but ignored.
- OTP codes are stored as salted hashes, expire after `OTP_TTL_MINUTES`, allow five attempts,
  and are deleted on success.
- Sending is limited by a per-contact cooldown (`OTP_COOLDOWN_SECONDS`) and hourly cap
  (`OTP_MAX_PER_HOUR`), plus per-IP and per-contact sliding-window limits.

### Authorization

- Job creation and job applications require a valid bearer session.
- Career selection, stage progress, preferences, and dashboard endpoints require a session.
- When `PARTNER_API_KEY` is set, partner referrals require the `X-Partner-Key` header.
- `/docs` and `/openapi.json` are disabled in production unless `ENABLE_DOCS=true`.

### Input handling and output encoding

- Pydantic models enforce lengths, allowed values, hex colours, name/contact formats, and
  draft key allowlists (draft payloads are capped at 32 KB).
- Job postings reject HTML angle brackets; accommodation values are allowlisted.
- The frontend passes every dynamic value through `esc()` before it reaches `innerHTML`.
- Server exceptions return a generic message; upstream provider errors are logged, not echoed.

### Abuse limits

An in-process sliding-window limiter protects login, OTP send/verify, drafts, referrals,
job listing/creation/application, TTS, STT, AI chat, and logout. For multi-worker or
multi-instance deployments, replace `SlidingWindowLimiter` with a shared Redis-backed limiter.

### Transport and headers

- CORS uses an explicit origin allowlist from `CORS_ORIGINS`; credentials are disabled.
- API responses set `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Permissions-Policy`, `Cross-Origin-Resource-Policy`, and `Cache-Control: no-store`.
- Request bodies over `MAX_BODY_BYTES` are rejected before parsing.
- Audio uploads are limited to `MAX_AUDIO_BYTES` and an allowlist of content types.
- The bundled nginx configuration sets a Content-Security-Policy, frame denial, and
  a no-sniff policy for the static frontend.

### Data handling

- `backend/digital_bridge.db`, `backend/data/`, `.env`, and generated bytecode are ignored by
  git and excluded from Docker build contexts.
- The SQLite database is not committed. Back it up and encrypt it like any personal data.
- Voice and AI provider calls may send text or audio to third parties; disclose this in the
  learner consent flow and configure `ADDIS_API_KEY` / `HUGGINGFACE_API_KEY` deliberately.

## Deployment Checklist

- [ ] Set `ENV=production`.
- [ ] Set `CORS_ORIGINS` to the real frontend origin(s). Do not use `*`.
- [ ] Keep `ENABLE_DOCS=false` unless the API reference must be public.
- [ ] Terminate TLS at a trusted proxy and forward only to the API.
- [ ] Set `TRUST_PROXY=true` only when a trusted proxy sets `X-Forwarded-For`.
- [ ] Replace the in-process rate limiter with a shared store for multiple workers.
- [ ] Serve `frontend/` through nginx (or equivalent) with the provided security headers.
- [ ] Persist `/app/data` on encrypted storage and restrict filesystem permissions.
- [ ] Rotate `PARTNER_API_KEY`, SMS webhook credentials, and AI provider keys.
- [ ] Run `python -m pytest tests -q` and a dependency vulnerability scan in CI.
- [ ] Review Amharic and English copy with native speakers and accessibility testers.

## Residual Risks

- The rate limiter is per process and resets on restart.
- SQLite is suitable for a single instance; larger deployments should move to PostgreSQL and
  add a migration tool.
- Draft resume tokens grant access to saved draft data to anyone holding the link. Treat them
  as secrets, shorten their lifetime, and avoid including sensitive values in drafts.
- Voice input relies on browser speech recognition and may be unavailable or inaccurate;
  keyboard and typed paths must remain fully functional.
- No email/SMS delivery provider is bundled. Without `SMS_WEBHOOK_URL`, development mode
  prints codes to the server console; production must configure a real sender.

## Reporting a Vulnerability

Do not open a public issue for security problems. Contact the maintainers privately with
reproduction steps, affected versions, and impact. Please allow time for a fix before
disclosure.
